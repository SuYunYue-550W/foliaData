## 1. 你的两个选择与合规边界

交互里你选了：授权类型 = **音乐平台会员/内容授权（推荐）**，落地范围 = **全都要（含 Windows 真解码）**。这两者存在必须讲清的硬冲突：

1. **会员/内容授权拿到的是什么**：平台服务端把对象混音**提前渲染**成普通 FLAC / AAC / MP4（立体声或 5.1）再下发。客户端拿到的是「一个音频文件」，用现成解码路径就能放，**不涉及杜比解码授权**。
2. **真对象式杜比解码要什么**：E-AC-3 JOC / AC-4 IMS 码流（带 JOC / OAMD 对象元数据）+ Dolby 官方解码器与渲染器（MS12 / DAX3 / AC-4 Consumer Decoder / Atmos Core for Windows）+ 产品认证 + 平台真的下发对象码流。Chromium（Electron 43）对 `audio/eac3`、`audio/ac4` 的 `canPlayType` 与 MSE `isTypeSupported` 都是 false；Web Audio 最多 8 声道离散、没有对象音频渲染；主线 FFmpeg 8.1 无 AC-4 解码器。
3. **本轮按「合规可达的最深边界」推进**：把「能合法拿到的最高格式」全链路补齐，把「本机杜比能力」如实标注，把「真解码」留成空注册表 + 预留接口，绝不用 HRTF 虚拟环绕（`surroundBranch.ts` / `orbitBranch.ts`）冒充杜比全景声。

## 2. 四种「杜比」形态（这决定了实现方式）

| 形态 | 本质 | 本应用要不要改 | 本轮处理 |
| --- | --- | --- | --- |
| `platform-rendered` | 平台已双耳渲染好的普通音频文件 | 不用解码器，只需能选到该档位 | **已支持**：全局 `atmos` 档位 + 汽水五档 |
| `object-based` | E-AC-3 JOC / AC-4 IMS 对象码流 | 需 licensed 解码器 + 渲染器 + 认证 | **不可用**：`dolbyObjectDecoding: false`，接口预留 |
| `os-takeover` | Win11 Dolby Access / Android DAX3 在 OS 音频层把立体声上混 | App 无需改、也**无法可靠检测/控制** | 设置页如实写「由系统决定」 |
| HRTF 虚拟环绕 | 本应用音效链把立体声上混成虚拟环绕 | 与杜比无关 | 明确排除，不注册进解码后端 |

## 3. 已实现（P0 全链路）

### 3.1　全局 `atmos` 档位贯通

`AudioQualityPreference` 从 5 档扩到 6 档：`standard | high | ultra | lossless | hires | atmos`。`atmos` 的语义是「平台已渲染的空间音频 / 杜比全景声曲目」，只在 provider 显式列出它时才会被请求。

| 层 | 改动 |
| --- | --- |
| `src/types/onlineMusic.ts` | 类型新增 `'atmos'`；注释写明它不是对象流、不是更高位深 |
| `src/services/onlineMusic/omni/playbackMethods.ts` | `AUDIO_QUALITY_LEVELS` 纳入 `atmos`；`UNLISTED_AUDIO_QUALITY_LEVELS` **仍排除** `ultra`/`atmos`，防止未知 quality key 打到固定键后端 |
| `src/stores/useAudioSettingsStore.ts` | `resolveStoredAudioQuality()` 保留已存的 `atmos` |
| `src/components/panelTab/AccountTab.tsx` | 默认音质下拉新增 `atmos`，选中时显示「非本机对象式解码」提示 |
| 缓存 | `ProviderAudioSource.quality` 记录实际档位，会员降级时不会把低档流缓存成高档 |

`omni.resolveAudioQuality()` 仍是「最近不高于偏好」解析：未声明 `atmos` 的 provider，一个已存的 `atmos` 偏好会安全落到它自己的最高真实档。

### 3.2　汽水音乐解锁五档

`src/services/onlineMusic/qishuiProvider.ts`（桌面端与安卓端实际注册的 provider）：

- `audioQualityLevels` 从无到有，解锁 `['standard', 'high', 'lossless', 'hires', 'atmos']`；
- 新增 `QISHUI_LEVEL_TO_APP`，把后端 `data.level` 映射回全局档位（`exhigh→high` 等）；
- `getAudioSource()` 用**后端实际返回的档位**而非请求档位记录 `quality`，避免会员降级时把低档流按高档缓存、下次误播。

两端协议**本轮无需改动、已核实支持**：`electron/qishui/qishui-api.js` 与 `android/.../assets/qishui/protocol.js` 都已有 `qishuiNormalizeAppQuality()`（`spatial|atmos|dolby|immersive → atmos`）、`QISHUI_QUALITY_RANK`（`atmos: 5`）、`availableQualities` 含 `atmos`，以及显式 quality 选流 + 会员降级兜底。

### 3.3　其余平台安全回退（不让未知档位静默降级）

QQ / 网易云 / 酷狗后端只认固定 quality key，传未知 key 会**静默降到 128 kbps**。本轮让 `atmos` 一律回退到各自最高真实档：

| 文件 | `atmos` 处理 |
| --- | --- |
| `qq/qqProvider.ts` | 回退链 `flac → 320 → 128`（`atmos` 从不被 *请求*，但已存偏好要能降级） |
| `netease/neteaseProvider.ts` | `mapQuality('atmos') → 'hires'`；scrobble 按 `hires` 上报 |
| `kugou/kugouProvider.ts` | `qualityValue('atmos') → 'high'`；`QUALITY_FALLBACKS.atmos` = `hires → lossless → high → standard` |
| `mods/folium/registries/omniProviders.ts` | mod 契约只有 4 档，`atmos → hires`（`ultra` 仍 `→ high`） |
| `qishui/qishuiPlayback.ts` | 加注释说明该 provider 未注册、`qishui-music-api` 只四档，真正解锁 atmos 的是 `../qishuiProvider.ts` |

### 3.4　能力如实标注（单一事实来源）

`src/platform/playbackCapabilities.ts` 新增 `DolbyPlaybackMode` 与 4 个字段，全部**如实**：

```ts
platformAtmosTracks: true,      // 平台已渲染曲目两端都能播
dolbyObjectDecoding: false,     // 本机无对象式解码（恒 false）
dolbyMode: 'platform-rendered',
hiResBitPerfectOutput: false,   // 会重采样，不是 bit-perfect（见 §6）
```

### 3.5　只读「空间音频与高解析」设置组

`src/components/modal/settings/pages/SpatialAudioCapabilityRows.tsx`（新增）+ `PlaybackPage.tsx` 引入。**没有开关**——目前没有一项是用户能在 App 内开关的杜比能力，做开关只会误导。只读状态条展示：曲目可播 / 对象式解码不可用 / Hi-Res 播放时重采样 / 系统级接管由系统决定 / Android 设备解码器探测结果。对象式解码那行读 `hasDolbyObjectDecodeBackend()`，将来真注册了 licensed 后端会自动翻成「可用」。

### 3.6　对象式解码后端预留接口（空的，不是假开关）

`src/services/audioCodec/dolbyDecodeBackend.ts`（新增）：`DolbySourceDescriptor`、`DolbyDecodeBackend` 接口 + `registerDolbyDecodeBackend` / `hasDolbyObjectDecodeBackend` / `findDolbyDecodeBackend` / `listDolbyDecodeBackends`。注册表初始为空，注释列明四项前置条件全缺。将来拿到 dev kit，改动集中在此处注册实现即可，UI 不用重写。

### 3.7　Android 设备能力探测（只探测，不改播放）

- `android/.../player/FoliaNativePlayerPlugin.kt`：`@PluginMethod getDolbyDeviceCapabilities()`，用 `MediaCodecList` 查设备有没有 `audio/eac3`/`audio/ac4`/`audio/ac3`/`audio/flac` 解码器；MIME 用字面量字符串（避开 `MediaFormat.MIMETYPE_AUDIO_AC4` 的 API 28 / minSdk 24 争议）。**不加载解码库、不改播放路径、不承诺支持对象式解码**。
- `src/services/playbackEngine/nativePlayerPlugin.ts`：新增 `DolbyDeviceCapabilities` 类型、插件方法声明与 wrapper。
- 设置页仅在 Android、插件存在时异步探测一次，失败显示「不可用」而非隐藏。

### 3.8　三语文案 + 单测

- `zh-CN / en / in` 新增 `account.qualityAtmos*` 与 `options.spatial*` 共约 21 个键，格式统一。

## 6. 未实现 / 明确不做（如实更正）

> **重要更正**：上一轮曾口头提到 Windows 侧会做「免重采样输出 + 系统杜比接管检测」。实际代码**只做了如实标注**：
> `hiResBitPerfectOutput: false`，设置页显示「播放时重采样」；系统级接管只写「由系统决定」，**没有实现可靠检测**（App 层通常也无法可靠判断 Dolby Access / DAX3 是否接管）。此处不声称已支持 bit-perfect 输出。

| 项 | 状态 | 原因 / 前置条件 |
| --- | --- | --- |
| Windows 真对象式杜比解码 | **未实现** | 需 Dolby 官方 dev kit + 产品认证 + 二进制解码/渲染库 + 平台对象码流；或重编译打了 codec patch 的 Chromium。当前四项全缺 |
| Hi-Res bit-perfect 输出 | **未实现** | `new AudioContext({ latencyHint: 'balanced' })` 未指定 `sampleRate`，跟随系统默认采样率；Android `setAudioAttributes(DEFAULT, true)` 未配高采样率/透传。192 kHz/24 bit 母带会重采样 |
| 系统杜比接管检测 | **未实现（只说明）** | App 层无法可靠检测/控制 OS 音频栈虚拟化 |
| QQ 官方 SDK 最高档（MASTER_TAPE / GALAXY / EXCELLENT / DOLBY） | **未接入** | 当前 `@yakult-green-tea/qq-music-api 3.3.3` 后端只支持 `m4a / 128 / 320 / ape / flac`；接官方 SDK 是另一条链路 |
| 酷狗蝰蛇全景声 2.0 / 母带、Spotify Lossless | **未接入** | 本轮只做安全回退；酷狗仍是 `hires`、Spotify 仍是 160/320 kbps Ogg Vorbis、YTM `ultra` 256 kbps 已是该链路上限 |

## 7. 真机验收清单

1. **汽水音乐**：会员账号下，设置 → 默认音质选「杜比全景声 / 空间音频」，选一首平台标记的空间音频曲目，确认能播、且音质回落提示符合会员权益；断开会员再播，确认不会出现「请求 atmos 却缓存成高档」的错档。
2. **QQ / 网易云 / 酷狗**：把默认音质设成 `atmos`（或旧版本残留该偏好），确认不会静默掉到 128 kbps，而是落到各自最高真实档。
3. **设置页**：播放控制页底部出现「空间音频与高解析」只读组，五项状态文案正确、无开关；Android 端多一行设备解码器探测结果。
4. **Windows**：Dolby Access 开启「Atmos for Headphones」时，普通立体声输出由系统虚拟化——确认 App 不谎称「已解码杜比」，也不因该组设置产生异常。
5. **Hi-Res**：播放 192 kHz/24 bit 母带，确认能播但设置页如实写「播放时重采样」，不出现「原样输出」表述。
