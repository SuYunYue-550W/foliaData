> 应用：`0.7.25.dev2`，`build: unofficial (unknown@dev)`，`origin: https://localhost`，Android 14 WebView

## 1. 错误码的官方定义

`20279` 出现在 `message="QQ app QR: musicu rejected (upstream 20279, global 0)"`，是 QQ 音乐上游返回的码。官方仓库三处一致认定：

| 来源 | 原文要点 |
|---|---|
| `.github/triage/login-playbook.json` → `qq-device-limit` | 「QQ 音乐账号的登录设备数已达上限」；症状：凭据交换阶段 `upstreamCode=20279`，随后 `get-login-user` 回 `code=1000` |
| `docs/qq-music-deployment.md:314` | 「账号的登录设备数已达上限（凭据交换返回 `20279`）时，登录窗口直接说明设备超限，下面一行告诉用户去哪里清：打开 QQ 音乐 App，进入「设置」，滑到最下面点「设备管理」，移除不用的设备后再扫码」 |
| `docs/qq-music-deployment.md:334` 排错表 | 「扫码后上游返回 `20279` → 账号的登录设备满了…serverless 部署换一次 `QQ_SESSION_SECRET` 或换一个部署，对 QQ 来说就是一台新设备」 |

**设备配额**（`zh-CN.ts:1899` 与 playbook 一致）：免费用户 **1 台**、绿钻 **3 台**、超级会员 **5 台**。

**为什么偏偏平板中招**：官方文档 `:224` 明确「每个新部署对 QQ 来说都是一台新设备」。平板是全新设备身份，若手机上 QQ 音乐 App 仍登着同一账号，免费账号的第 2 台设备会直接被拒。诊断里 `scanned=false`、`polls=2`、`elapsedMs=7041` —— **二维码刚生成、还没扫就被拒**，正符合「新设备身份一注册就撞设备上限」，不是用户扫码操作有误。

## 2. 为什么界面只显示「平台拒绝 · refused / 请稍后重试」

**本地代码其实已完整内置 `device-limit` 识别与中文提示**，只是这次没命中：

| 已有实现 | 位置 |
|---|---|
| `'device-limit': { kind: 'C', action: 'retry', details: true }` | `src/services/onlineMusic/login/loginFailureCase.ts:24` |
| 判定常量 `20279` / `auth.device-limit` / `login.device-limit` | `src/services/onlineMusic/qq/qqProvider.ts:709-720` |
| 命中后返回 `case: 'device-limit'` | `qqProvider.ts:791` |
| 中文提示「设置 → 设备管理 → 移除不用的设备」 | `src/i18n/locales/zh-CN.ts:1829, 1896-1899`；`qqProvider.ts:1125`；`loginCaseTexts.ts:18` |

**没命中的两个原因（都与 Android 平台直接相关）**：

1. **后端没给结构化字段**。`reportsDeviceLimit()` 要求 `upstreamCode === 20279` 或 `upstreamErrorKey='auth.device-limit'` 或 `failureHint.key='login.device-limit'`。本次响应是 `code 0` + 一句英文文本里嵌 `upstream 20279`，三个字段全无 → 判定为假。
2. **客户端兜底路径是桌面专属**。`isQqDeviceLimit()` 的第二条路要读 `window.electron.getLoginDiagnostics` 的主进程 `qq-auth.upstream-result` 记录；**Android WebView 没有 `window.electron`**。代码注释自己写明「更旧的后端没有这个字段…**桌面版**再去那里找」，`zh-CN.ts:4331` 也写「**网页版目前只能识别微信扫码的这种情况**」。

于是落到 `qqHintFailure()` 的 `login.rejected` → `case: refused (kind C)` → 通用「请稍后重试」。

补充两条诊断细节：
- `login methods shown: qqmusic (no picker)`：登录渠道由后端 `/login/channels` 宣告决定（`qqProvider.ts:585-599`），只宣告 `qqmusic` 就不显示选择器。官方文档说**微信通道的 20279 会直接出现在 `upstreamCode` 上**（3.3.0 起还有 `upstreamErrorKey`）—— 若后端宣告 `wechat`，客户端反而能认出设备超限。这属于**后端配置**，客户端改不了。
- `self-check: not run`：官方 `:310` 写「在手机上取消不跑自检、不给这块帮助」，平板走的是这条取消路径，所以没出现「换网络/重启」和自检结论。

## 4. 解决步骤（按顺序）

1. **清理登录设备（唯一根治）**：手机打开 QQ 音乐官方 App → 「设置」→ 滑到最底部 →「设备管理」→ 移除不再使用的设备 → 回平板**重启 Folia** → 重新扫码。
   - 免费账号只有 1 台配额，手机上那个占位的设备必须清掉或退出登录。
2. **换通道 / 换账号 / 提配额**：让后端 `/login/channels` 宣告 `wechat`（结构化字段更全，客户端能直接给出设备超限提示）；或换一个设备没满的账号；或绿钻(3 台)/超会(5 台)提高配额。
3. **别连续刷新二维码**：后端有 backoff，频繁要码会触发 `104604`（操作太频繁，冷却 30 秒）或 `login.rate-limited`。等 30 秒以上再试。
4. **自建/公共 Serverless 后端注意**：换部署或换 `QQ_SESSION_SECRET` 对 QQ 就是一台新设备，会反复撞 20279（官方 `:224/:334`）。密钥定下来后不要随便改。
5. **「换网络 / 重启 Folia」这两条对本题无效** —— 它们是官方给通用网络类失败的建议，20279 是账号配额，不是网络问题。

## 5. 可选的代码改进（未实施，需确认）

只动一处即可改善**提示**，不能绕过服务端配额：

- 在 `src/services/onlineMusic/qq/qqProvider.ts` 的 `reportsDeviceLimit()` 增加「从 `message` 文本正则匹配 `upstream\s*20279`」的兜底，让 Android WebView 在「无 `window.electron` + 后端无结构化字段」时也能把 `case` 判成 `device-limit`，从而显示「设置 → 设备管理 → 移除旧设备」而不是「请稍后重试」。
- 改动范围仅限这一个文件（必要时加一条 i18n 兜底文案），**不碰桌宠、共用登录 UI、两端共用桥接文件**，避免上一轮那种牵连。
- 若要落地，重打 APK 并按在线发布方式交付。

**如实说明**：真正让账号能登录的仍然是第 4 节第 1 步（清设备）；代码改动只让人少走弯路。
