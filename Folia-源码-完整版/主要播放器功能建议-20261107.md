# Folia · 主要播放器功能建议

> 生成时间：2026-11-07 ｜ 性质：**只读核实 + 建议，本轮未改动任何源码**
> 范围：只谈「播放器」——出声链路、进度与传输、队列、音效、系统媒体控制、播放质量。
> 桌宠、构建、签名与交付不在本文范围（见 [项目改进建议-20261107.md](./项目改进建议-20261107.md)）。
> 核实方式：直接读取 `/workspace/folia-sonnet` 当前源码，逐条给出可自行复核的文件与行号。

---

## 结论先行

这个播放器的**功能密度已经远超一般音乐 App**：桌面端有 Web Audio 双 deck 自动混音、分轨分析、十段 EQ + 调音台、沉浸式音效、歌词全链、OBS/Stage/Remote 投屏、Jam 同听；Android 有一整套 ExoPlayer 原生 DSP（协议 v3）、前台服务 + MediaSession、通知栏/锁屏、原生交叉淡化。

**所以不建议再加新音效或新模块。** 真正的问题是一句话：

> **同一首歌在 Android 与 Windows 上不是同一个播放器，而界面把这个差异藏起来了。**

最值得动的三件事：**把「哪些能力在当前平台生效」显式化**（先消灭静默失效）、**让本地歌曲也走原生播放链**、**补桌面端系统媒体控制**。三条都不新增功能，只是把已有能力完整交付给用户。

## 2. P0 · 建议马上处理

### P0-1 能力落差是「静默」的：自动混音在 Android 上能开、开了无效

**证据**

| 位置 | 内容 |
|---|---|
| `useAppPlaybackQueue.ts:213` | `isEnabled: automixEnabled && !isNowPlayingStageActive && !nativeActive` → Android 恒 `nativeActive`，**自动混音被硬关** |
| `PlaybackPage.tsx:166-203` | 自动混音开关无任何平台门控，且展开「交叉淡化时长 / 音量交叉曲线」两个子项 |
| `useAppFoundation.ts:177` | `window.electron?.setAutomixEnabled?.(...)` —— 设置只推给 Electron |
| 对照 `KaraokeRow.tsx:69` + `useKaraokeModeStore.ts:18-26` | 项目**已经有一套正确做法**：`KaraokeAvailability` + `karaoke.unavailableNative` 灰置并说明原因 |

**后果**：Android 用户打开自动混音，还顺手调了交叉淡化曲线，实际什么都没发生。而「交叉淡化」在 Android 原生其实是**可用的**（`crossfadeTo` 已实现），只是被同一个开关绑着一起失效——这是最容易被误判成「功能坏了」的一类问题。

**建议**

1. 抽一个 `playbackCapabilities.ts` 作为**平台能力的单一事实来源**：`webAudioGraph` / `automixAnalysis` / `crossfade` / `nativeDsp` / `systemMediaControls` 等布尔位，由运行时环境一次算出。
2. 所有「Web Audio 专属」设置项统一走 `KaraokeRow` 那套灰置 + 原因提示，别再逐个打补丁。
3. Android 上**拆开**自动混音与交叉淡化：前者灰掉（依赖离线分轨分析，短期不可能搬到端侧），后者保留并接原生 `setCrossfadeAhead` / `setCrossfadeCurve`（`FoliaNativePlayer.kt:554-562` 已有接口）。

成本约半天，收益是消灭一整类「开了没反应」的用户反馈。

### P0-2 本地歌曲没有进原生播放链，一条歌两套行为

**证据**

| 位置 | 内容 |
|---|---|
| `nativePlaybackEngine.ts:106-111` | `supports()` 明确排除 `blob:` / `data:`，只放行 `http/https/content/file` |
| `useNativePlaybackRuntime.ts:57-65` | 注释原文：「blob 地址（本地歌）原生吃不下，那种歌整首回落到 `<audio>`，**等缓存搬进私有目录（后面的阶段）再说**」 |
| `useAppAudioOutput.ts:72-74` | `nativeTakes` 同源判断；注释「媒体缓存走本机回环地址，原生能读」——**说明通路其实已经存在** |

**后果**：同一用户的「在线歌」与「导入的本地歌」落在两套音频栈上，行为不一致。

| 维度 | 在线歌（原生） | 本地歌（WebView `<audio>`） |
|---|---|---|
| 后台 / 锁屏续播 | 前台服务保障 | WebView 挂起后不保证 |
| 通知栏 / 锁屏 / 媒体键 | MediaSessionCompat | 由 Web `navigator.mediaSession` 兜（原生模式下 `audioRef` 无 src，实际失效，见 `useMediaSessionBridge.ts:126-129`） |
| 十段 EQ / 调音台 / 沉浸音效 | 原生 DSP 全量 | Web Audio 图（实现不同、听感不同） |
| 交叉淡化 / 自动混音 | 原生交叉淡化 | 桌面端那套 |
| 频谱 / 可视化数据源 | 原生 SpectrumAnalyzer | Web AnalyserNode |
| 预取、地址 TTL、失败恢复 | 全链路 | 部分不适用 |

**建议**

1. **短期（推荐）**：本地歌取源时把 `blob:` 换成原生可读的 URI。项目已有 `LocalAudioServer.kt`（本机回环 HTTP）与 `supports()` 对 `content://` / `file://` / `http://` 的放行，改动集中在取源那一步，不必动播放状态机。
2. **中期**：导入时把本地歌落一份到应用私有目录缓存，与 `mediaCacheStore` 合并，统一走 `file://`；顺带消除 `blob:` URL 在 WebView 重建后失效的隐患。
3. **兜底**：若决定保留回落，至少在播放页明确标注「本机歌曲使用兼容播放，后台与系统控制受限」——不要让用户自己撞出来。

### P0-3 桌面端缺系统级媒体控制，只有任务栏缩略图按钮

**证据**

| 位置 | 内容 |
|---|---|
| `electron/main.cjs:2893-2935` | `updateWindowThumbarButtons()` 只注册 3 个 thumbar 按钮（上一首 / 播放暂停 / 下一首） |
| `electron/preload.cjs:264-268` | 对外只有 `updateTaskbarControls` / `thumbar-action` |
| `useMediaSessionBridge.ts` | 用的是浏览器 `navigator.mediaSession`；且要求 `audioRef.current` 存在且 `audioSrc` 就绪，Android 原生模式下本来也走不通 |
| [电脑端与手机端功能对比.md](./电脑端与手机端功能对比.md) §3 | 已把「媒体会话 / 通知栏 / 锁屏 / 耳机按键」列为 Android 原生专属 |

**后果**：Windows 上全局媒体键、音量面板/锁屏的播放控制、蓝牙耳机按键都不可用，只有把鼠标移到任务栏图标上才能控制。这是桌面播放器最基础的「系统融入度」。

**建议**

1. **最低成本**：用 `globalShortcut` 注册 `MediaPlayPause` / `MediaNextTrack` / `MediaPreviousTrack` / `MediaStop`，覆盖绝大多数键盘与耳机按键，半天可完成。
2. **完整方案**：Windows 接 `SystemMediaTransportControls`（原生模块或成熟类库），macOS 接 `MPRemoteCommandCenter`；元数据统一取 `selectDisplaySong` / `selectDisplayPlayerState` / `selectDisplayDuration` 这套**显示层**，别读 raw `playerState`——`useMediaSessionBridge.ts:16-23` 记录了「标题与进度不是同一首歌」的历史 bug，重犯代价很低。
3. **真机核实**：先确认 `navigator.mediaSession` 在当前 Electron 43 的 Windows 下实际映射到什么范围，别把「代码里有」当成「系统里有」。

## 3. P1 · 播放行为与可观测性

### P1-1 断点续播：重启后回到歌曲开头

**证据**：`persistPlaybackCache.ts` 只写 `last_song` / `last_queue`；`useSessionRestoreController.ts:46-49, 187-198` 明确「Restore normally leaves it alone so the session comes back **paused**」。`adoptNativePlaybackState()` 只在 **WebView 重建而原生服务仍在播** 时接管位置（`useSessionRestoreController.ts:108-113`），进程真重启时不覆盖。

**建议**：把 `last_position_ms` 与 songKey 一起持久化（节流 ~5 秒即可），恢复时按 songKey 匹配后 `nativePlaybackEngine.seek()` 或写 `audio.currentTime`。**优先采信原生服务仍在播的位置**（现有 `readNativeQueueState()` 已是这个思路），避免出现「界面显示 2:30、实际从 0:00 出声」。对长音频与播客尤其明显。

### P1-2 「上一首」是队列前一项，不是听过的上一首

**证据**：`playbackNeighbors.ts` 的 `prevQueueIndex()` 是纯下标计算；`createQueueMutations.ts:86` 用 `queueIndexOf(playQueue, currentSong)`；`prefetchService.ts:46` 的 `PREFETCH_COUNT_PREV = 1` 也按队列预取。`listeningArchive/` 有完整收听记录，但那是统计与年度总结，不参与传输决策。

**后果**：随机播放、搜索后单曲起播、手动插队之后按「上一首」，回不到真实听过的那首。这是主流播放器普遍具备、这里唯一缺席的传输基础行为。

**建议**：独立维护 `playbackHistory`（songKey 栈，与 `playQueue` 解耦），`handlePrev` 优先弹栈；队列洗牌 / 替换时保留历史。改动集中在 `usePlaybackQueueController`，不碰音频层。

### P1-3 AB 循环 / 片段循环缺席

**证据**：全项目检索 `abLoop|loopRange|sectionLoop|bookmark` 零命中；`usePlaybackStore` 只有 `duration` 与 `lyricTimelineOffsetMs`，没有区间标记。

**建议**：在 `currentTime` motion signal 层加 A / B 两个 mark，到 B 回跳 A。Web 路径写 `audio.currentTime`，原生路径调 `nativePlaybackEngine.seek()`（已存在，且 `seek()` 会正确复位「只进不退」的位置基准，见 `nativePlaybackEngine.ts:193-201`）。练琴、语言跟读、扒谱场景都用得上，也很适合做成竞赛演示里一页能讲清的差异化功能。

### P1-4 播放质量对用户不可观测

**证据**：`AudioQualityPreference` 有 5 档（standard → hires，`src/types/onlineMusic.ts:13`），播放页有 `onAudioQualityChange`（`buildPlayerPanelModel.ts:275-276`），但 `ProviderAudioSource` 与播放器面板里**没有「实际拿到的码率 / 格式 / 是否无损 / 是否命中缓存」的回显**。

**后果**：用户选了「hires」，实际被平台降级成 128k 也无从知道；版权降级、地址过期换链（`ONLINE_AUDIO_URL_TTL_MS = 20 分钟`）全程静默发生，排查时只能翻日志。

**建议**：播放页「歌曲信息」加一行实际音质 + 音源 + 缓存命中；把 `playbackFailurePolicy` 的换链 / 降级结果做成轻量提示。对音质敏感的用户，这是最直观的信任信号。

### P1-5 音频焦点双管理需要核实（核实项，非断言 bug）

**证据**：`FoliaNativePlayer.kt:822` 是 `created.setAudioAttributes(AudioAttributes.DEFAULT, true)` —— ExoPlayer 自身会启用音频焦点管理，且第二个参数 `true` 即内建的 `handleAudioBecomingNoisy`（**拔耳机 / 蓝牙断连暂停其实已由它处理，不要重复建议**）。同时项目还有 `audio/FoliaAudioFocus.kt` 自定义单例。

**建议**：确认两者没有同时处理 duck / pause 造成竞态；并把 `AudioAttributes` 从 `DEFAULT` 改为显式声明 `USAGE_MEDIA` + `CONTENT_TYPE_MUSIC`，让系统正确选择音量流、蓝牙编码与「正在播放」设备路由。

## 5. 结合竞赛 / 答辩

- **把「双栈」讲成架构选择而不是缺陷**：Android 走 ExoPlayer + 原生 DSP（省电、后台续播、系统媒体控制），Windows 走 Web Audio 图（能跑分轨分析与自动混音），再用一份平台能力表约束 UI 与设置。这比堆功能列表更能体现架构能力，也正好呼应你网安背景里「按攻击面收敛能力暴露」的思路。
- **演示只挑一个卖点**：推荐「自动混音」或「原生 DSP 实时调音台」，配 30 秒录屏 + 一张能力矩阵图。功能太多时，全演示等于没演示。
- **别在材料里写「两端功能完全一致」**：评委一旦在手机上打开自动混音发现没反应，整页可信度会掉。写成「按平台能力分级交付」反而加分。

## 6. 如果只做三件事

| # | 事项 | 预估 | 风险 |
|---|---|---|---|
| 1 | 抽 `playbackCapabilities.ts` + 自动混音 / 交叉淡化拆开灰置（P0-1） | 半天 | 零，不碰音频层 |
| 2 | 本地歌接原生 URI，统一出声链路（P0-2） | 1–2 天 | 中，需真机验证后台 / 通知栏 / 焦点 |
| 3 | 全局媒体键 + 断点续播（P0-3 + P1-1） | 1 天 | 低 |

第 1 条建议先做：它不需要真机、不碰运行时代码，却能立刻把「功能看起来坏了」变成「功能明确标注为不支持」。
