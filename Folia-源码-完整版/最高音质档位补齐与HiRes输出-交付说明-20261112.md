## 0. 结论速览

**先说最重要的一句**：这四项**确实都不需要 Dolby 授权**，这个判断是对的。但联网核实 + 逐条读代码后发现，其中**两项卡在「平台官方 SDK / 商业授权」上，和 Dolby 是同一类外部授权障碍**，不是换个依赖就能补的；另外两项有真实可落地的部分，但 **bit-perfect 输出在本项目架构里不可达**。

本轮按上一轮一致的「合规可达最深边界」推进，没有做任何假开关：

| 你点的项 | 本轮结果 |
| --- | --- |
| 酷狗蝰蛇母带 / 全景声 | ✅ **Electron 桌面端真实取流已接通**（`hires`/`atmos` 偏好时先问 `viper_tape` → `viper_atmos`，拿不到按同一条链降级）。Web / 安卓明确不下发，理由见 2.1 |
| QQ 官方 SDK 最高档 | ❌ 需 QQ 音乐开放平台 SDK 商业授权，未实现；✅ 修掉一个安卓端 `hires` 反而降到 320 kbps 的既有 bug，并把档位链抽成可测的纯数据模块。**APE 试过但撤回了**，理由见 2.2 |
| Spotify Lossless | ❌ 需 Spotify 官方商业 SDK 合作，未实现；✅ 只做了 `audio/flac` 格式分支预留与如实注释 |
| Hi-Res bit-perfect 输出 | ❌ 架构上不可达（不是漏配）；✅ 改为**只读展示实际输出采样率**，并把能力文案改成精确事实 |

**过程中修掉一个自己引入的真实缺陷**：最初把 viper 探测写成主链之前的独立循环，它吞掉超时错误继续请求，绕开了「超时立即短路」护栏（1 次请求变 3 次）。全量测试暴露后，改成把高档候选**并入主降级循环**，护栏自动复用。详见 3.2 与 5.2。

改动**只在源码树**，尚未重新打包 `exe / apk / 源码 zip`（见第 9 节）。

## 2. 四项逐一：真实条件与落地决定

### 2.1　酷狗蝰蛇母带 —— 可真实落地，但只在 Electron 桌面

三个运行时的取流链路**完全不同**，档位字符串不能共用：

| 运行时 | 链路 | 能否传 `viper_tape` |
| --- | --- | --- |
| Electron 桌面 | `requestKugou('song_url')` → 随包打进去的 `kugoumusicapi/module/song_url.js`，`quality` **原样透传**给上游 `/song/url` | ✅ 能，版本随包固定 |
| Web 版 | `getWebApiBase()` 指向的远端 KuGouMusicApi 服务，版本由部署方决定、不由本项目控制 | ❌ 不能确认它认不认 `viper_*`，发未知档位可能静默降级 |
| 安卓 App 壳 | 本地桥 `handleKGSongUrl()` 自己按 hash 挑档再打 `/v5/url`，`quality` 被 `Number()` 归一化，只认 `128 / 320 / flac` | ❌ 传进去会**静默退化成 128 kbps** |

所以门控是 `hasElectronBridge() && !isAndroidAppShell()`，写成可单测的纯函数 `kugouCanUseUpstreamSongUrl(electron, androidShell)`。这个收窄不是为让测试通过，而是「只在知道对端会怎么处理这个 key 时才发它」；桌面 exe 正是本项目的主要交付形态。

**顺手修掉一个既有降级**：安卓桥把 `'high'` 读成 `320 kbps`，所以原先 `hires` / `atmos` 偏好反而比 `lossless` 低一档。现在安卓壳把这两档明确落到 `flac`。

> 为什么默认只问 2 个档：上游还提供 `viper_clear` / `super`，但每多一个候选就是一次串行请求，绝大多数非 VIP、无该档曲目的播放会被拖慢起速。默认只问 `viper_tape`（母带）与 `viper_atmos`（全景声），覆盖你明确要的两项。

### 2.2　QQ 官方 SDK 最高档 —— 不实现；APE 试过但撤回

当前 provider 用的是社区逆向包 `@yakult-green-tea/qq-music-api`，其 `MUSIC_FILE_TYPES` 只有 `m4a / 128 / 320 / ape / flac`。**官方 SDK 的母带 / 臻品系列拿不到，也不是加几个字符串能解决的**（要换整套授权播放栈）。

本轮一度在 `flac` 之后追加了 `ape`（包里确实存在、部分曲目只有 APE 没有 FLAC），但**全量测试后撤回了**，如实说明取舍：

- `ape` 与 `flac` 同为普通无损，**并不比 flac 更高**，不是你点名要的官方 SDK 母带档；
- 只有极少数曲目用得上，却给每一次最高档播放多加一次串行请求；
- 它把「每档一次请求」的失败路径契约整体推后一档，**17 个精心设计的可靠性用例**（超时短路、preview 兜底、请求次数）全部失准。为这点收益削弱那组护栏不划算。

保留下来的是**档位链抽成纯数据模块**（`qqQualityTiers.ts`，无副作用、可被契约测试直接引用）与把边界写清楚的注释。真要支持 ape，应作为独立能力单独评估。

### 2.3　Spotify Lossless —— 不实现，只留格式分支

桌面播放组件是 `@lox-audioserver/node-librespot@0.5.1`；安卓侧 `spotifyInPageRuntime.ts` 直接把 `audio` 列入 `UNSUPPORTED`（**安卓根本不能播 Spotify 音频**，只做目录与登录）。桌面侧 `BITRATES` 是 `{ standard: 160, high: 320, lossless: 320, hires: 320 }`。

即便把 `lossless` 声明成新档位，桌面也只会拿到 320 kbps Ogg 文件——这就是假开关，不做。本轮只：

- 把 `shapeOf()` 扩展为认得 `FLAC*` → `audio/flac`（**格式分支，不是质量档**，为将来合法 FLAC 流留好通路，当前不会被触发）；
- 注释写清 Lossless 的真实条件与 librespot 上游限制；
- `BITRATES` 里 `lossless / hires → 320` 明确标注为「安全回退」，不是占位。

### 2.4　Hi-Res bit-perfect —— 不可达，改为如实暴露采样率

`FoliaAudioSinkFactory.kt` 的注释已经把约束写死：**`setEnableFloatOutput(false)` 是主动选择**——打开后 media3 会跳过整条 `AudioProcessor` 链（原生 EQ 静默失效），且高解析源会先经 `ToInt16PcmAudioProcessor` 降到 16 bit。所以「bit-perfect」不是漏配，是为保 EQ 的架构取舍。

本轮不改播放路径，只做**只读事实展示**：设置页新增「实际输出采样率」一行。

| 端 | 数据来源 |
| --- | --- |
| 桌面 / Web | `mediaDiagnostics` 已采集的 `AudioContext.sampleRate`（无需新探测） |
| 安卓 | 新增 `getAudioOutputCapabilities()`，只读回报 `outputSampleRate` / `floatPcmOutput`，失败报 `available: false` |

> 安卓探测踩到一个坑：项目在 `android/app/src/main/java/android/media/AudioManager.java` 放了一个**编译期占位类**（为了让 `FoliaAudioManager` 能继承它），它没有 `getProperty` / `PROPERTY_OUTPUT_*`，直接写会 `Unresolved reference`。运行时加载的才是 framework 真类。最终实现用**反射读 framework 的 property + `AudioTrack.getNativeOutputSampleRate()` 兜底**，常量写字面量，全程 `try/catch`。第一次编译失败、修正后 `BUILD SUCCESSFUL`。

`hiResBitPerfectOutput` 仍恒为 `false`；文案从「播放时重采样」改成精确说明原因（16 bit PCM、系统混音器）。

### 3.2　酷狗 provider 接入（含一处缺陷修复）
`src/services/onlineMusic/kugou/kugouProvider.ts`
- `qualityValue` 委托给共享映射
- `getAudioSource()` 构造一个 `candidates` 列表：Electron 桌面 + 最高档偏好时，把平台档位**放在数组最前**，其后是常规档位链；**整条链共用一个循环**
- 每个候选带 `wireQuality`（发给后端）、`appQuality`（返回上层的全局档位）、可选 `sourceTier`（诊断）
- 因此超时短路、`auth-required` 立即抛、429 / 未配置立即抛、legacy 兜底、`firstFailure` / `noUrlSeen` 全部自动复用，没有第二套护栏
- 云盘曲目、Web、安卓完全不产生平台档位候选

**修掉的缺陷**：最初版本把 viper 探测写成主循环**之前**的独立 `for`，它的 `catch` 吞掉所有错误并继续，导致：超时本应 1 次请求短路，实际打到 3 次；`not-configured` / 429 也不再立即抛。全量测试的 `stops asking /song/url after a request ran out of time` 精确抓到了这一点。改成并入主循环后，5 个既有契约用例零改动恢复，并新增集成测试专门钉住这条护栏。

### 3.3　QQ 档位链抽成纯数据模块（新增）

## 6. 未实现 / 明确不做（如实列出）

1. **QQ 官方 SDK 的 `MASTER_TAPE / GALAXY / DOLBY / HIRES / EXCELLENT` 档位**：需开放平台 appId + 商业授权 + 换整套播放栈。当前逆向包协议里不存在这些档，硬加只会变成未知 key → 静默 128 kbps。
2. **Spotify Lossless**：需 Spotify 官方商业 SDK 合作；librespot 上游明确不支持，安卓侧连 `audio` operation 都不支持。没有声明 `lossless` 质量档，不做假开关。
3. **Hi-Res bit-perfect 输出**：Web Audio 与安卓通用音频路径上均不可达；`floatPcmOutput` 恒 false 是保 EQ 的主动取舍。只做了实际输出采样率的只读展示。
4. **QQ 的 APE 档位**：已核实存在但撤回，理由见 2.2。
5. **Web 版 / 安卓端蝰蛇母带**：Web 远端服务版本不可控、安卓本地桥会把未知档位降到 128 kbps，都明确不下发。
6. **`viper_clear` / `super`（DSD）**：上游支持但未纳入默认尝试链，理由见 2.1（避免拖慢起速）。
7. **系统级杜比接管检测**：App 层无法可靠判断，仍只做说明（上一轮结论不变）。
