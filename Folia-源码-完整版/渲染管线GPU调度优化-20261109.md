---

## 一、先说结论

上一轮核实过：项目里**没有**一条全局统一、名叫 `RenderPipeline` 的抽象管线，而是「统一的模式调度层 + 28 个可视化模式各自带一条渲染链」，另有 4 个独立 HTML document 各跑各的 rAF。

所以这次没有去改 `machi` 的 three.js 多 pass、`nebbia` 的手写 WebGL2 多目标、或 `sonnet`/`tempera` 的 Pixi Filter 链——**动那些等于动 28 个模式的画质，风险与收益不成比例**。

做的是补一层**微渲染引擎（micro render scheduler）**：一个轻量、自包含、默认开启的 GPU 帧预算调度内核。它不碰任何 shader / pass，只在「帧节拍」这一层把已有的三个总闸接成闭环，并让多个渲染 document 互相让预算。

> **「微渲染引擎」在本轮的明确定义**：不是新的渲染器，而是「统一帧预算的调度微内核」——采样真实帧耗时 → 纯函数状态机决策 → 落到已有的帧率/分辨率总闸 → 跨窗口协调 → 上下文丢失降载。

## 二、现状缺口（为什么这么设计）

| 已有机制 | 文件 | 局限 |
|---|---|---|
| 后台渲染总闸 | `utils/backgroundRenderGate.ts` | 退后台一帧不画，但**只管当前 window**；壁纸层明确不装它 |
| 帧率限流 | `utils/frameRateLimiter.ts` | 用户手选固定档（30/60/90/120），装完就不动 |
| 渲染分辨率夹取 | `utils/renderPixelRatio.ts` | 用户手选固定上限，装完就不动；改档会广播 `resize` 触发整页重排 |
| 帧耗时诊断 | `utils/frameTimingDiagnostics.ts` | 有 p90 / `renderHealth` / 刷新率估算，但**只写调试报告**，默认关闭，不驱动任何决策 |
| 引擎级上下文恢复 | `lattice` / `harmonyOverlay` / `machi` / `nebbia` / `pendolo` | 5 处都在 canvas 上 `preventDefault()` 并自己重建，**但没有应用层的「丢失时降 GPU 预算」策略** |

三个真空：

1. **诊断与调度断开**：实测帧耗时只用于「用户报卡时分流」，运行时不做任何自适应。
2. **档位互不感知**：帧率档与分辨率档各管各的，负载重时不会协同降级；用户手选一档后，低端机仍会硬扛。
3. **多 document 抢 GPU**：主窗口、壁纸层、桌面歌词、OBS 源各自满帧，谁也不知道别人在画。

### 动手前修正的一处判断

我在排查时一度认为「项目没有 `webglcontextlost` 处理」。**这个判断不成立**：全项目有 5 处引擎级恢复实现（见上表）。本轮补的是**应用层降载策略**，在 `window` 捕获阶段监听、只读不改事件、不调 `preventDefault()`，与各引擎自己的恢复流程完全不冲突。文档按事实修正，避免把「已有能力」当缺口重复造。

## 四、决策内核参数

| 参数 | 值 | 含义 |
|---|---|---|
| 坏窗口判定 | `p90 > 1.5 × 目标间隔` 或 慢帧占比 `> 25%` | 目标间隔按当前档位与实测刷新率取较大者 |
| 好窗口判定 | `p90 < 1.1 × 目标间隔` 且 慢帧占比 `< 8%` | 中性窗口**不清零**已累计证据 |
| 降档 | 连续 **2** 个坏窗口 | 有滞回，单帧抖动不动档 |
| 升档 | 连续 **6** 个好窗口 | 明显比降档保守 |
| 变更冷却 | **2500 ms** | 冷却期内坏窗口继续累计，一结束立刻降下一档 |
| 分辨率变更冷却 | **8000 ms** | 因为改档会触发整页 `resize` 重排 |
| 上下文丢失保持 | **8000 ms** | 期间只降不升，给引擎重建留余量 |
| 采样窗口 | 1000 ms / ≥8 帧 | 样本不足不决策（刚恢复前台） |

**降档路径**（用户基准决定起点，级数只是「相对用户让了几格」）：

| 用户设定 | 0 级 | 1 级 | 2 级 | 3 级 |
|---|---|---|---|---|
| 不限帧 `off` | off | 60 | 30 | 30 |
| 120 | 120 | 90 | 60 | 30 |
| 90 | 90 | 60 | 30 | 30 |
| 60 | 60 | 30 | 30 | 30 |
| 30 | 30 | 30 | 30 | 30 |

帧率见底后，**只有**用户显式打开「允许自动降渲染分辨率」才继续降像素比（`2 → 1.5 → 1.25 → 1 → 0.75 → 0.5`）。升档严格逆序。

## 五、与用户设置的关系（最重要的边界）

| 约束 | 实现 |
|---|---|
| 用户手选档位永远是**天花板** | 状态机只输出「用户基准往下让几级」，回升终点就是用户设的那一档，绝不会把用户限的 60fps 升到 120fps |
| 调度器**不写 localStorage、不改 store** | 只调两个底层总闸函数；关掉开关时按用户当前设置完整还原 |
| 用户中途改档位 | 端口每秒读一次存储 → 状态机检测到基准变化 → 重建状态并落回用户档 |
| 关闭总开关 | 停采样循环、关跨层通道、移除监听、还原用户帧率与分辨率 |
| 默认行为 | 调度**默认开**；「允许自动降分辨率」**默认关**（避免整页重排） |

设置位置：`设置 → 图形 → 性能` 分组，在「渲染分辨率上限」下面新增两行，含 zh-CN / en / 印尼语三语文案。

### 跨 document 协调

`BroadcastChannel('folia.microRender.v1')`，2 秒心跳、6 秒超时清理。多个渲染层同时活跃时**非主层先让一档**帧预算（`minimumFrameRateStep`），主窗口保持满预算。壁纸层传 `ignoreVisibility: true` —— 它本来就要求「应用退后台照常画」，不能被主窗口那套可见性判断冻住。

> 通道不可用时（部分 WebView / `file://` 环境）自动退化为单 document 自调度，**功能不缺失**。没有引入 Electron IPC，桌面端与安卓端行为不分叉。

## 八、仍需真机确认

沙箱没有 Windows / Android 图形环境，以下都**没有实测**：

1. 默认开启后，播放页顺畅时档位应**完全不动**（用户设 `off` 仍是 `off`，不会凭空装上限帧器）。
2. 制造负载（同时开壁纸层 + 复杂可视化模式）→ 观察是否逐级降到 60 / 30，负载消失后是否回升。
3. 设置页手选 30 FPS 后，调度器不应升过 30；关闭总开关应立刻还原用户档。
4. 主窗口 + 壁纸层同时开时，壁纸层让一档、主窗口保持。
5. 触发 WebGL 上下文丢失（安卓 WebView 切后台 / GPU 重置）→ 降一档且 8 秒内不回升；各引擎自己的重建流程不受影响。

另：`dist/` 当前停在 **Electron/PWA 版**（含 `sw.js`）。要打 APK 必须重跑 `npm run cap:sync:android` 重建 capacitor 版 dist，别直接在现有 dist 上 `assembleDebug`。

```
/root/.codebuddy/artifact/2f8a7d30-9c21-4f0b-1d62-4790797b8000/backup-gpu-20261109/
```

回滚 = 删除 6 个新增文件 + 从备份还原 6 个修改文件（`useVisualizerSettingsStore.ts` 本就没动）。另外把 `folia.microRender.enabled`、`folia.microRender.allowPixelRatioScaling` 两个 localStorage key 清掉即可，无其它持久化状态。

若只想临时停用而不回滚代码：设置页关掉「自适应 GPU 调度」，或直接 `localStorage.setItem('folia.microRender.enabled','false')` 后刷新——调度器会还原用户档位并停掉采样循环。
