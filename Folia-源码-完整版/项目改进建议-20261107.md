# Folia 桌宠鲸鱼版 · 项目改进建议

> 生成时间：2026-11-07 ｜ 性质：**只读核实 + 建议，本轮未改动任何源码**
> 核实方式：直接读取 `/workspace/folia-sonnet` 当前源码、`/workspace` 交付物清单、以及前几轮复查/构建记录。

## 结论先行

这个项目现在的状态是「**功能密度很高，工程基线偏弱**」。桌宠从应用内 DOM 一路改到系统级浮层，两端各自解决了真问题（跨应用置顶、开屏单一渲染源、拖拽、覆盖安装），但支撑这些改动的**版本控制、凭据管理、产物管理、自动化校验**没有同步跟上。

最值得投入的不是再加功能，而是三件半天能做完、且不碰运行时代码的事：**凭据出包并换签名**、**纳入 git 并打 tag**、**清理顶层产物让下载页成为唯一入口**。

以下按优先级分级。每条都附现状证据，便于你自己复核。

## P0 · 建议马上处理

### P0-1 签名凭据已随源码包分发出去，应视作已泄露

**现状证据**

| 项 | 值 |
|---|---|
| `android/keystore.properties` | 含明文 `storePassword` / `keyPassword`（弱口令）+ 打包机绝对路径 `/workspace/folia-sonnet/android/whale-pet.keystore` |
| `android/app/build.gradle:71-83` | debug 与 release **共用同一把 keystore**，注释写明「固定 debug 签名，保证跨环境打包签名一致」 |
| 刚交付的 `Folia-源码-安卓版-20261106.zip` | 校验脚本明确列 `android/whale-pet.keystore`、`android/keystore.properties` 为「应含」——**私钥与口令一起进了可分发的 zip** |
| `package.json build.win` | 只有 `artifactName / target / icon / extraResources`，**无 `certificateFile` / 代码签名配置** → exe 必然触发 SmartScreen「未知发布者」 |

**后果**：任何拿到源码 zip 的人都能签出同签名 APK，对已安装用户构成覆盖安装/冒充升级的通道（Android 同包名同签名可直接覆盖）。这是 debug 密钥不是生产证书，所以不算高危漏洞，但属于**分发卫生与供应链实践问题**，且与你的网安专业方向直接相关，答辩时被问到会是明显扣分项。SmartScreen 告警则影响演示观感。

**建议**
1. 源码包与仓库里只保留 `keystore.properties.example`（占位值），真实凭据走**环境变量 / CI Secret / 本机不入库文件**，并加进 `.gitignore`。
2. debug 与 release 签名**分离**：debug 用 Android 默认 debug.keystore 即可，release 单独一把、不进任何分发包。
3. 已分发的这把**重新生成**，后续正式包换用新签名（注意：换签名后旧版无法覆盖安装，需在下载页写清「首次换签名需先卸载」）。
4. 条件允许时给 exe 配代码签名证书（OV/免费方案均可），或至少在下载页公示 SHA256，让「未知发布者」有可核验的替代路径。

### P0-2 项目不在版本控制下

**现状证据**：`git rev-parse --is-inside-work-tree` → `fatal: not a git repository`。`vite.config.ts` 构建时会执行 `git rev-parse --short HEAD` / `--abbrev-ref HEAD`，实测两版源码包构建日志都打印 `Could not get commit hash` / `fatal: not a git repository`（被 try/catch 吞掉，所以不失败，但构建身份退化成 `unknown@dev` / `unofficial`）。

**后果**
- 这几轮连续重构（浮层链路 → 桌面端独立解耦 → P0 修复 → 源码拆分）**无法 diff、无法回滚、无法 bisect**。
- 源码包靠手工 `zip` 生成，无法回答「这个 MD5 对应哪一份代码」——而下载页恰恰是靠 MD5 做版本标识的。
- 平板端诊断报告里 `build: unofficial (unknown@dev)` 就是这个问题的直接表现。

**建议**
1. 初始化仓库，首次提交打 tag（如 `v0.7.25-whalepet`），之后每次交付一个 tag。
2. `.gitignore` 至少覆盖：`node_modules/`、`dist/`、`release/`、`models/`、`android/app/build/`、`android/.gradle/`、`.windowtolayer-src/target/`、`android/local.properties`、`android/keystore.properties`、`*.apk`、`*.exe`、`*.zip`。
3. 把 **commit hash + MD5 + 构建时间** 三元组写进下载页，替代现在只靠 MD5 的做法。
4. CI 里已有 `ci.yml` / `android-release.yml` / `electron-release.yml` 等 17 个工作流，直接把「构建身份注入」接进去即可，不用新建体系。

### P0-3 `/workspace` 顶层产物混放，存在装错版本的实际风险

**现状证据**（顶层 9 个二进制交付物，跨 3 天、文件名相近）

| 日期 | 文件 | 大小 |

| 11-04 | `Folia鲸鱼桌宠版-0.7.25-完整交付包.zip` | 489 MB |
| 11-04 | `Folia鲸鱼桌宠版-源码-安卓与Windows.zip` | 101 MB |
| 11-05 | `Folia-WhalePet-split.zip` | 2.6 MB |
| 11-05 | `Folia-桌宠鲸鱼版-debug.apk` | 128 MB |
| 11-05 | `Folia-桌宠鲸鱼版-系统置顶桌面版-Setup.exe` | 320 MB |

**后果**：之前确实发生过「电脑端 exe 是 11-04 旧构建，11-05 改动一份没进」的误判，根因就是新旧同名产物混放。`改动说明.md` / `电脑端与手机端功能对比.md` / `项目整体复查报告-20261105.md` 三份文档也靠「顶部追加注记」打补丁，正文结论大量过期，读的人要自己分辨哪段有效。

**建议**
1. 顶层只保留**当前有效版本**（exe、apk、两版源码 zip），其余移入 `archive/2026-11-04/` 或删除。
2. 明确「**在线下载页是唯一版本入口**」，页面顶部固定展示当前版本 / 构建时间 / commit / MD5。
3. 文档改成**单一事实来源**：重写一份 `DELIVERY.md`（当前状态），把三份历史文档移入 `docs/history/`，不再靠顶部注记叠加。

## P1 · 架构债（影响稳定性与后续开发效率）

### P1-1 桌面端仍是「半解耦」，不是注释宣称的完全独立

**现状证据**
- `src/whalePet/desktop.ts:43-51`：只给主窗口 DOM 鲸鱼注入 `.whale-pet{visibility:hidden!important;pointer-events:none!important}`，**不销毁实例**。
- `src/whalePet/init.ts:139-207`：桌面端不走浮层代理，返回**真实桌宠实例** `pet`。
- `src/whalePet/linkage.ts:47-107`：鼓点起舞 / 歌词气泡 / 久坐提醒仍完全依赖主 WebView 的 `requestAnimationFrame` + `setInterval`。

**后果**：主窗口最小化到托盘或被节流时 rAF 停摆，而置顶桌宠窗口还常驻 → **联动立刻失效**；同时两个 `<video>` 持续解码、双份漫游与位置持久化在跑。上一轮修掉的是拖拽 P0 与定时器泄漏，这个结构性残留没动。

**建议**：把联动状态改为**主进程持有并推送**给桌宠窗口（或让桌宠窗口自行订阅播放事件），桌面端主 WebView **根本不创建**桌宠实例而不是隐藏。这样既省一份解码，也彻底消除「两处都弹气泡 / 两处都写位置」的双份副作用。

### P1-2 设置项与 i18n 文案和新架构互相矛盾

**现状证据**：`WhalePetSetting.tsx:138-142` 已加 `overlayMode` 与 `overlayHint = '（当前为系统级窗口，该项不生效）'`（这点比旧结论好，已有提示）；但 `src/i18n/locales/zh-CN.ts:6629/6632` 仍写着「碰边反弹、贴角落」「关闭则遮挡时自动隐身不挡按钮」——这些是**应用内 DOM 时代**的行为，系统级窗口下并不存在。

**建议**：按平台条件渲染，把浮层模式下无实效的项**真正隐藏或置灰**，同时改写文案；Android 浮层里被 `pet.js` 显式 `return` 的漫游 / 双击彩蛋 / 拖动换动作 / 弹窗避让 / 触边反弹，要么从桌面端实现移植补齐（桌面端已做，可复用），要么统一标注「暂不支持」，别让「不生效」提示和「碰边反弹」说明同时出现。

### P1-3 桌宠资源 50 MB 存两份，靠手工复制且无校验

**现状证据**：`public/whale-pet/` 97 文件 / 50 MB，`android/app/src/main/assets/whalepet-assets/` 97 文件 / 50 MB；`pet.js` 在 `src/whalePet/`、`public/whale-pet/`、`android assets` 三处 MD5 恰好一致（`6e53efbf…`），但 `ci/`、`scripts/`、`package.json`、`build/` 中**没有任何同步或一致性校验脚本**。

**后果**：之前吃过「只跑 `assembleDebug` 导致 Web 产物不更新」的亏，正是这类手工同步的典型症状；APK 里还白白多带一份资源。

**建议**：以 `public/whale-pet/` 为**唯一源**，加一个 `cap sync` 前置脚本自动拷贝 + MD5 校验并纳入 `build:capacitor` 链；Android 侧改为运行时从 `public` 产物读取或只保留必需子集，可望省下约 50 MB。

### P1-4 构建链靠环境变量切换，缺防呆

**现状证据**：`dist/` 对两端互斥（Electron/PWA 版含 `sw.js`+`manifest.webmanifest`，Capacitor 版无），切换全靠 `ELECTRON_DEV` / `ELECTRON` / `FOLIA_BUILD_TARGET` 三个环境变量；脚本名相近（`build:capacitor` / `build:electron:dir` / `dev:electron:dist`）。交叉打包 Windows exe 时 GitHub 源实测不通，需手动设 `ELECTRON_MIRROR` + `ELECTRON_BUILDER_BINARIES_MIRROR` 走 npmmirror 才能成功。

**建议**
1. 两端改用不同 `outDir`（`dist-electron/` / `dist-capacitor/`），从根上消除互相覆盖。
2. `cap sync` 前加一道断言：检查产物 `index.html` **不含** PWA manifest，否则直接报错退出。
3. 镜像变量写进 CI / `.npmrc` / 构建脚本，不再依赖每次手敲。

## P2 · 质量与可验证性

### P2-1 桌宠新架构几乎没有自动化测试

**现状证据**：`test/unit/whalePet/` 只有 1 个文件 `linkageLogic.test.ts`。而最容易回归的 `electron/whalePetWindow.cjs`（几何插值、clamp、定时器、IPC 来源校验）、`FloatingWhaleService.kt`（ValueAnimator 竞态、旋转重算）、`build/installer.nsh`（NSIS 钩子）**零覆盖**。

**建议**：补三类纯逻辑单测（几何插值与屏幕边界 clamp、位置持久化读写与异常兜底、QQ 失败分类全 upstream 码表驱动）；NSIS 用 `makensis` 做编译期检查——上一轮验证「钩子是否真展开」用的编译期标记法可以直接固化成 CI 步骤，成本很低。

### P2-2 真机验证靠用户截图，应制度化

**现状**：连续多轮交付都附「沙箱无 Windows/Android 图形环境，无法验证显示与拖拽」，问题基本靠你发截图/视频才发现（双鲸鱼、结束后下移、拖不动、安装器弹框）。

**建议**：做一张 8~10 项发版自测表（置顶是否生效、拖拽是否跟手、开屏是否单实例且平滑、托盘「显示窗口」、覆盖安装两个弹框、旋转/改尺寸落点、QQ 登录失败提示、后台联动是否持续…），每次发版随包附上，勾选回传。能显著减少来回轮次，也天然形成竞赛材料里的「测试验证」章节。

### P2-3 QQ 20279 之外的失败码尚未逐一验证

**现状**：上一轮已修「本地桥透传 `upstreamCode/failureHint/primaryFailure` + `code:0` 终态兜底 + message 里 `upstream 20279` 正则」。但账号被封、账号受限、扫错 App、`104604` 操作太频繁在平板端是否仍被误报成通用 `refused`，没有逐项验证过。

**建议**：把官方 `.github/triage/login-playbook.json` 的用例做成表驱动单测，覆盖全部 upstream 码，一次性确认 Android 网页版路径的归类正确率。另需记住：**设备数超限本身只能在 QQ 音乐 App「设置 → 设备管理」清设备**，代码只改善提示，别在文档里给人「已修复」的错觉。

## 结合你的专业与竞赛背景（可能比上面的工程项更有价值）

### A. 把「系统级桌宠」从 UI 小功能重新定位成技术壁垒

创新创业计划书里，桌宠容易被当成装饰性功能。但这里实际做到的是：**跨进程/跨应用的窗口合成 + 单一渲染源的几何过渡 + 两套原生宿主的解耦设计**（Android `TYPE_APPLICATION_OVERLAY` + 前台服务；Windows `alwaysOnTop('screen-saver')` + 独立 BrowserWindow；共用 Web 资源层）。这属于端侧系统能力，比普通前端组件有说服力得多。

建议整理成**一页架构图 + 30 秒真机录屏**（开屏单实例飞到落点、跨应用置顶、拖拽持久化），放进「技术可行性 / 核心技术」章节，配一句量化描述（如「两端共用 2868 个前端文件、原生层各自独立」），比堆功能列表有效。

### B. 补一份轻量威胁模型，形成「安全设计」章节

以你的网安背景，这个项目有现成素材：悬浮窗权限的滥用面、Capacitor 桥暴露给 WebView 的原生方法、`file://` WebView 与 `chrome://inspect`（已修为仅 debuggable 开放）、debug 签名可被同签名包覆盖（P0-1）、NSIS 曾按映像名全局 `taskkill`（已改为按安装路径限定）。整理成一页「风险 → 缓解措施 → 残余风险」表，既是真实改进，又能与 WorkBuddy 校园安全运维系统的主线互相呼应，答辩时是差异化优势。

### C. 版本与交付节奏要能对外解释

当前 `0.7.25.dev2` / `unofficial (unknown@dev)`，构建身份不可追溯。建议固定版本号规则 + 每次发版由 git log 自动生成 CHANGELOG，在线下载页加「版本历史」折叠区。竞赛材料里，评委很在意「这个团队能不能稳定交付」，版本可比性是最便宜的证据。
